# Launch Database — Streamline & Rebuild Roadmap

> Single source of truth for where this product is going. Any Claude (or person) opening this repo should read `CLAUDE.md` first (what the product is + how we work), then this file (what we're building, in order).

## Context

The platform works but *feels* clunky to operate. The root cause is the data model: a "project" is a generic node in a rollup-of-rollups tree (`Client → EC → Service Area → Job-leaf`, all `projects` rows with `is_rollup` flags). That tree is why organization is a struggle, the contract mechanics feel over-complicated, manual fields don't auto-fill, and the pipeline is full of confirmation pop-ups.

Direction: make it **simple, streamlined, techy/minimal**. The unifying fix is to make the **Service Area / Concentrator the unit of work**, with **jobs as line items inside it**. Billing sums, client visibility, contractor timeclock, maps, and materials all hang off that.

Decisions locked:
- **Test data is disposable** — wipe and stand up the clean model directly (no risky in-place migration).
- **Engineering Contract stays visible & segregated; EC presence ⟺ RUS program.** Non-RUS (BAU/GFR/Other) has no EC and sits directly under the client.
- **Invoices: scrap the AI-vision template** for a simple, reliable, configurable one.
- **Remove the compliance audit-log + retention feature** (unnecessary).
- **No confirmation pop-ups** in the pipeline — instant changes + undo bar.
- **Employee self-signup:** `@launchfiber.com` email + standing shared signup code; self-select non-privileged role; manager/admin admin-only; username + email unique; same-name blocked.
- **Contractor accounts:** unique single-use invite codes generated by admin (no domain requirement).
- **Bake future (materials + map) hooks into the Phase 2 schema now**; implement later.
- **Drop the orchestration ceremony** — modern Claude Code provides sub-agents/parallelism/plan-mode as built-in tooling.
- Sequence below is the recommended order; earliest phases stabilize + clean up, then the keystone unlocks the rest.

## Operating model (how we work)

- **Head Claude (CEO).** Thin router: owns the schema, conventions, **directives**, task briefs, and all merges; reviews at integration, not at every step. Does NOT re-do or red-team-gate others' work.
- **The team is multiple instances run by Carter and coworkers** (spreads usage across accounts + real teamwork). Each works in **its own clone on its own branch** (one person = one clone = one branch; no worktrees) and may spawn its own sub-agents. They execute a written brief and push to **their own branch (never main)**; CEO verifies + merges.
- **Coordination = a per-instance brief in `briefs/` on main.** Each instance pulls main, reads its brief, works only in its scope, pushes its branch, flips status to `DONE — ready for review`. CEO owns the briefs doc; instances never edit it.
- **Directive control is centralized to the CEO.** Only the CEO issues/changes directives, scope, schema, or conventions. An instance needing such a change stops and routes a sign-off request to the CEO (`BLOCKED — needs CEO` in its brief); the coworker relays it. No unilateral directive changes.
- **Sequencing: foundation first, then fan out.** Build the foundation solo (with sub-agents): docs/handoff, Phase 0 cleanup, and the Phase 2 keystone data-model rebuild. Only once the data model is stable do downstream tracks (billing, timeclock, client portal, KMZ sync, real-time) fan out to Claude 2/3 — building parallel work on a shifting foundation is the thing we avoid.
- **Coordination substrate = documents, not check-ins.** This `ROADMAP.md` + lean `CLAUDE.md` + a per-track brief for each handed-off task. Created BEFORE any fan-out so every instance shares one source of truth.
- **No orchestration ceremony.** Sub-agents/parallelism used with judgment. The old manual pipeline (manager-never-codes, saturation red-teams, branch-isolation hooks, rogue countermeasures) is retired.
- **Cost discipline — cheap + accurate over haste.** Always prefer the lower-token approach as long as accuracy holds. No fanning out agents or exhaustive multi-pass workflows for their own sake — use the minimum that yields a correct result. Cut verbosity, redundant exploration, speed-for-its-own-sake; never cut accuracy or correctness.

## Target model

```
Client
 ├─ Engineering Contract  (RUS only — visible, segregated)
 │    └─ Service Area / Concentrator   ← THE unit (status, map, materials, client-visible, billable)
 │         ├─ Job: Permitting     → employee · billing type · rate · hours · $ · status · dates
 │         ├─ Job: Design / Inspection / Construction → …
 └─ Service Area / Concentrator  (non-RUS: BAU/GFR/Other — no EC)
      └─ Jobs …
```

- **Service Area total = sum of its jobs** → feeds the Invoicing tab.
- **Hours** logged by a person against a job roll into that job's $ and into the Hours tab (per person + job).
- Client sees: their service areas, each one's status, done/remaining, and (later) the map + materials.

## Guiding principles (every phase)

1. **Streamline relentlessly** — fewer buttons/fields/clicks; minimal/techy look (graphics later).
2. **Auto-populate anything derivable** — "if X then Y" with manual override.
3. **No confirmation pop-ups** — optimistic updates + the existing undo bar (`undo_buckets`, `public/js/undo_bar.js`, `routes/undo.js`).
4. **Real-time over polling** — push via SSE.
5. **Build on existing data plumbing** where sound; restructure presentation + entry.

## Phase 1 — Diagnostics, QA sweep & stabilization

**Goal:** find every bug (including silent ones), build a durable safety net, then fix what's worth fixing pre-rebuild.

- **Diagnostics logger (full clickstream, testing-grade):** capture every interaction + JS errors, unhandled rejections, failed/slow API calls across every portal → a backend diagnostics table + an admin diagnostics view. Built as a *testing tool*, not permanent telemetry: master on/off toggle, time/volume-bounded retention, and **one-click purge** so the volume never piles up.
- **Agent-driven QA sweep (on the clean Phase 0 DB):** an agent exercises every page/function/interaction across all portals, adds test data, verifies things populate and portals interact correctly. Runs against the disposable DB; destructive flows (delete/bill) handled carefully. *Seeds* the bug list — a fast finder, not a durable test.
- **Expand the Playwright E2E suite** (`npm run test:browser`) to cover each portal's critical flows so bugs stay caught in CI — the durable layer the agent pass can't provide.
- **Triage + fix:** (a) bugs in code we're *keeping* (auth, splice, files, timeclock backend, invoicing core) → fix now; (b) bugs in the old rollup admin/pipeline we replace in Phase 2 → let the rebuild absorb (don't double-fix).

**Done when:** diagnostics logger live, the QA sweep + Playwright expansion produced a triaged bug list, and the "keep" bugs are fixed.

## Phase 2 — Service-Area-with-jobs rebuild + templates (the keystone)

**Goal:** replace the rollup tree with the clean model + auto-population + no pop-ups + fast bulk setup. Biggest daily-pain fix; everything downstream depends on it.

- **Schema (new migration `0063+`):** service areas as first-class units, jobs as line items. Reuse `ec_service_areas`, `jobs`, `job_assignments`, `time_entries`, `pricing_entries`; retire `is_rollup`/`rollup_level`/`rollup_key` from the everyday model. Each job: discipline, employee, billing type, rate, hours, status, $, dates.
- **Reserve future hooks now:** per-service-area materials table (BOM rows: item, qty, unit, optional cost) + map/KMZ attachment + client-visibility flag, plus a materials section stub in the projects-tab expanded detail view. Schema defined now; auto-populate + UI built in Phases 7 & 10.
- **Admin UI rebuild** (`public/admin.html` + `public/js/projects_tab.js`, `project_cascade.js`, `project_picker.js`): Client → EC (RUS) / direct service areas (non-RUS) → **service-area detail = a clean inline-editable job table**.
- **Auto-population & conditional logic** (`routes/projects.js`, `engineering_contracts.js`, `jobs.js`, `contracts.js` + cascade/picker JS).
- **Templates + bulk creation:** new service area auto-spawns its standard job set with defaults; bulk-create many concentrators from a pasted/imported list.
- **Kill pipeline pop-ups** (`routes/design_pipeline.js`, `permits.js`, `inspection.js` + tab JS): one-click/drag, optimistic, undo-bar.
- **Live lists** via `routes/_sse.js`.

**Done when:** create client → (EC if RUS) → service area → jobs with auto-filled fields; bulk-spin concentrators; pipeline moves with zero pop-ups; live updates; future hooks present in schema.

## Phase 3 — Accounts & self-signup

- **Employee self-signup** (`auth.js` + new endpoint + `public/login.html`): name, `@launchfiber.com` email, shared signup code, self-selected non-privileged role, own username + password (bcrypt, min 10). Manager/admin admin-only. Username + email unique; same full name blocked. Rate-limited.
- **Contractor invite codes:** admin generates a **unique single-use code** per contractor (no domain check); new `signup_codes`/invite table (or reuse `client_portal_v2` token infra); code consumed on use; assigns contractor role.
- **Admin code management** (`public/js/admin_users.js`): rotate shared employee code; generate/revoke contractor codes; promote/demote roles.

**Done when:** employees self-register with domain + code; contractors register with one-time codes; admin manages codes + elevated roles.

## Phase 4 — Billing, invoices & money view

- Job $ → service-area total → **Invoicing tab** (`routes/billing.js`, `invoices.js`, `revenue.js`; `public/js/billing_tab.js`, `bulk_bill_modal.js`).

**Done when:** jobs sum into a clean templated PDF invoice; money view shows ready-to-bill, margin, and who owes what.

## Phase 5 — Contractor timeclock (dead simple)

- Contractor sees **only their assigned service areas** → pick/type job → hours + description → submit. No cascade.
- Hours attach to the job → roll into the service-area bill (Phase 4) + Hours tab under person + job.
- Files: `public/timeclock.html` + JS, `routes/time_entries.js`, `hours_csv.js`, `job_assignments`.

**Done when:** an untrained contractor logs hours against a service-area job; it appears in billing + Hours.

- **Test-data wipe is destructive** — authorized; confirm timing before Phase 0.
- **Audit-log removal touches many route files** — strip incrementally.
- **Railway deletions are irreversible** — provide the map; Carter executes.
- **No email verification on signup** — mitigated by domain + shared code (employees) and single-use codes (contractors); accepted tradeoff.
- **Real-time + desktop folder-sync are the heaviest lifts** — sequenced late.
