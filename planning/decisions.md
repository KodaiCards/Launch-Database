## D021 — Wake-watcher: exit-on-change, not `while true` (corrects the D004/D017 command) (2026-07-01)
**Decision:** The wake-watcher command in every charter (CEO.md, AUDITOR.md) is **replaced.** A `( while true; do …; sleep N; done ) &` loop **never exits, so it never wakes a Claude Code agent** — a background task re-invokes its agent only when it **EXITS** (and it must be a harness-tracked background task, NOT a detached `&`, which gets reaped). New pattern: poll `git ls-remote origin refs/heads/main` and **`exit 0` the moment the tip changes** (heartbeat-exit after ~60 min otherwise); on wake → `git pull origin main`, re-read your thread, re-arm. **Mandatory baseline (correctness does NOT depend on the watcher): CHECKPOINT-PULL** = `git pull origin main` at boot, before + after every increment/commit, before any long verify, and before reporting. Worker→Planning is unaffected (push to your branch; Planning's exit-on-change watcher — verified working this session — catches it).
**Reasoning:** Both CEO + Auditor cloud instances couldn't get woken (Carter, 2026-07-01); root cause = the never-exiting loop. Planning hit + fixed the identical bug in its own watcher this session, so the corrected pattern is battle-tested. Checkpoint-pull guarantees the comms loop closes even if a sandbox won't persist background tasks at all.
**Alternatives:** Read the background loop's stdout buffer (rejected — the agent never reads it, no turn is injected); block on a Monitor/until-wait (fine for an idle HOLD worker, wrong for an actively-building one — left as each agent's option, not the mandate).
**Refinement (2026-07-01, after the CEO + Auditor field-tested it):** both worker instances confirmed their **cloud/Cowork harness may not persist a background process across turns AT ALL** (the Auditor's `disown`/`nohup` watcher was dead by the next turn). ⇒ For WORKERS, **checkpoint-pull / boundary-fetch is THE mechanism, not a fallback** — the exit-on-change watcher is optional best-effort; don't spend effort persisting it. **Idle HOLD workers are NOT to idle-poll (no CronCreate loop — wasted tokens):** Planning posts the dispatch to their thread AND flags Carter to give them a turn ("pull main"). Planning's OWN watcher (local, harness-tracked) is verified working and stays. Both workers independently adopted boundary-fetch, so the comms loop is now self-sustaining.
**Refinement 2 (2026-07-01, Carter's insight):** the reaped kind (`nohup`/`disown`/`&`) ≠ a **harness-tracked** `run_in_background` task — the latter re-invokes the agent WHEN IT EXITS (Planning's `Monitor` proves this works locally). So workers now **ARM a harness-tracked `run_in_background` exit-on-change watcher on boot** (poll the target ref — `main` for CEO/Auditor, the CEO branch for C1/C2 — `exit` on change → wakes the agent → it pulls, acts, and RE-ARMS). Boot prompts updated with the exact command. **Boundary-fetch remains the guaranteed fallback** (if the cloud harness still drops the task across idle turns). Whether the harness-tracked kind survives an *idle* cloud worker is the open question — self-confirms on the next worker boot cycle; if it fires, this becomes the primary wake + the idle-nudge goes away.
**Refinement 3 (2026-07-02, Carter observed — the open question resolved NO for cloud):** the cloud workers **warn but do NOT redeploy** after the watcher exits → their harness (unlike Planning's local one) does NOT turn a background-task exit into a new turn. So the exit-watcher is **best-effort only for cloud workers; it cannot be relied on to wake them.** The GUARANTEED mechanism = **boundary-fetch at the START of every turn** (a worker is only current while actively running) — now an ⛔ ABSOLUTE MUST at the top of every boot prompt (still arm+re-arm the watcher per Carter, but correctness rides on boundary-fetch; confirm "watcher armed" in the first post). **ROLE BOUNDARY (Carter's correction):** the **CEO** watches + verifies + smoke-tests C1/C2 before integrating; **Planning watches ONLY the CEO + Auditor and reacts to the CEO's INTEGRATED reports — Planning does NOT verify C1/C2 raw pushes** (doing so = overstep into the CEO's lane). Planning's `Monitor` re-pointed to `ceo|auditor` branches only. True idle auto-wake for cloud would need server-side scheduled routines (RemoteTrigger — heavier/polling); parked unless Carter wants zero-touch badly enough.
**Refinement 4 (2026-07-02, Carter's key insight — CORRECTS ref3's pessimism):** the exit-on-change watcher failed for a fixable reason — **EXITING drops the running-task count to 0 → the container resets → stale.** The fix (what Planning's own watcher already does) = a **persistent `Monitor`**: it NEVER exits, it *emits* a wake event on each change while staying running → tasks-running stays ≥1 → **the container never resets** → the worker wakes per event AND stays warm. So cloud-worker self-wake **IS achievable** (Carter: "1 running task so the container never resets, and the cost isn't high" — correct). All four boot prompts switched from `run_in_background`-exit-on-change to a persistent `Monitor` (git-ls-remote poll, emit-on-change, `persistent:true`). Boundary-fetch stays as belt-and-suspenders. Running workers were told on-thread to switch (they can't see the boot-prompt change mid-session).
